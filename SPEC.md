# Question Set Studio — Functional & Data Spec

This document describes what the app does, the data it manages, and the
contracts between its pieces — so both the person extending the code and
the person just configuring/using it have one place to check "how is this
supposed to work."

## 1. Goal

Build practice sets for a child and grade their handwritten attempt at one,
all running locally with DeepSeek as the only external dependency. A set
comes from one of two sources:

- **The past-paper bank:** real Cambridge (CAIE) questions, cropped
  automatically from uploaded question paper PDFs, with the official mark
  schemes as answer keys (§12).
- **AI generation:** fresh, exam-pattern-matched questions written by
  DeepSeek from a blueprint, optionally inspired by uploaded reference
  papers (§6).

## 2. Roles (informal — there's no login/auth in this app)

- **Admin/parent**: uploads past papers, defines patterns, generates
  question sets, reviews graded results.
- **Student (child)**: solves a printed question set on paper; doesn't use
  the app directly except to have their photographed answer sheet uploaded
  on their behalf.

## 3. The three-stage flow

```
 Admin page                Generate page              Submit & Evaluate page
┌────────────────┐        ┌─────────────────┐        ┌───────────────────────┐
│ Upload past     │        │ Pick a Pattern   │        │ Print a Question Set   │
│ papers (PDF/MD) │──text─▶│ + source docs    │──────▶ │ → child solves on paper│
│                 │        │ → DeepSeek       │  Q's   │ → photograph it        │
│ Define Patterns │        │   generates a    │        │ → DeepSeek vision grades│
│ (exam blueprint)│──spec─▶│   Question Set   │        │   it against the hidden│
└────────────────┘        └─────────────────┘        │   answer key            │
                                                        └───────────────────────┘
```

## 4. Core concepts & data model

| Entity | What it is |
|---|---|
| **SourceDocument** | An uploaded past-year paper (or notes). Stores the original file plus extracted plain text. Used only as reference material fed into the generation prompt — never shown to the student, never copied verbatim by design instruction to the model. |
| **Pattern** | The exam blueprint / "spec": subject, grade, sections, and per-section question type + count + marks. Validated against [`config/pattern.schema.json`](config/pattern.schema.json). This is the main lever for controlling what generated papers look like. |
| **QuestionSet** | One paper. Its `source` is either `ai`, generated by DeepSeek from a `Pattern` (+ optional `SourceDocument`s), or `bank`, picked from `BankQuestion`s (no pattern). Has a status (`generating`/`ready`/`failed`). |
| **Question** | A single question: section, type (MCQ/VSA/SA/LA/CASE_STUDY, or PAST_PAPER for bank questions), text, options (MCQ only), marks, difficulty, and a **hidden** `expected_answer` + `rubric` used only for grading. Bank questions also link to their `BankQuestion`, whose image is what gets printed. |
| **PastPaper** | An uploaded Cambridge question paper plus, optionally, its mark scheme. Holds the paper code read from the footer (e.g. `0444/21 May/June 2023`), the mark scheme's maximum mark, a status (`processing`/`ready`/`failed`), and a list of paper-level warnings from the automatic checks. |
| **BankQuestion** | One question extracted from a `PastPaper`. Holds the cropped image (canonical) and the extracted text (lossy for maths), the marks read from its `[n]` brackets, sub-parts, topics, any question-level warnings ("flags"), and the official mark-scheme rows as text and as a cropped image. |
| **Submission** | One attempt: a child's photographed answer sheet(s) against a specific `QuestionSet`. |
| **Evaluation** | The graded result of a `Submission`: total marks, overall feedback, and one `EvaluationItem` per question (extracted answer, marks awarded, correctness, feedback). |

Full field-level detail is in `backend/app/models.py`, which is the source
of truth; this doc describes intent, not every column.

## 5. The Pattern spec (`config/pattern.schema.json`)

A Pattern is deliberately generic — not tied to one subject or grade — so
the same mechanism covers any CBSE subject/class. Shape:

```jsonc
{
  "name": "CBSE Class 10 Science - Sample Paper Pattern",
  "subject": "Science",
  "grade": "10",
  "total_marks": 49,               // informational; not enforced against sections
  "duration_minutes": 90,
  "general_instructions": ["..."],
  "sections": [
    {
      "name": "A",
      "instructions": "Multiple choice questions, 1 mark each.",
      "question_type": "MCQ",       // MCQ | VSA | SA | LA | CASE_STUDY
      "num_questions": 10,
      "num_to_attempt": null,       // set if this section offers internal choice
      "marks_per_question": 1,
      "difficulty_mix": { "easy": 0.5, "medium": 0.4, "hard": 0.1 }
    }
  ]
}
```

Non-technical editing path: the Admin page's pattern editor is a proper
form — name/subject/grade fields, a repeatable "Sections" list (name,
question type dropdown, question count, marks, optional internal-choice
count, optional difficulty mix), with total marks/questions computed and
shown live. No JSON is required day-to-day. Required fields use native
browser validation (a name/count/marks left blank is caught before the
request is even sent), and the payload is still validated server-side
against `config/pattern.schema.json` as a second line of defense. Power
users get an "Advanced: view/edit raw JSON" panel (collapsed by default)
that mirrors the form live and can be pasted into or out of — editing the
JSON and clicking "Apply" loads it back into the form fields, which stay
the single source of truth for what actually gets saved. See
`frontend/js/admin.js` (`formToConfig`/`configToForm`).

## 6. Generation contract

Input: a `Pattern`'s `config_json` + up to ~12,000 characters of combined
extracted text from the selected `SourceDocument`s + free-text extra
instructions.

DeepSeek is instructed (see `SYSTEM_PROMPT` in
`backend/app/services/generation.py`) to act as a CBSE paper-setter and
return exactly one question per blueprint slot, as JSON:

```jsonc
{
  "questions": [
    {
      "section": "A", "question_type": "MCQ", "text": "...",
      "options": ["...", "...", "...", "..."],   // MCQ only, else null
      "marks": 1, "difficulty": "easy",
      "expected_answer": "...", "rubric": "..."
    }
  ]
}
```

**Count enforcement:** after each response, the actual per-section question
counts are compared against the blueprint's `num_questions`. On a mismatch,
generation retries once with an added note telling the model exactly what
was wrong (e.g. `section 'A': expected 10, got 8`). If the retry still
doesn't match, the `QuestionSet` is marked `failed` with that description
in `error_message` rather than silently saving a partial/incorrect set —
nothing partially-generated ever reaches the printable view. See
`_expected_section_counts`/`_actual_section_counts`/`_describe_count_mismatch`
in `generation.py`, and `backend/tests/test_generation.py` for the retry
and failure paths (exercised by stubbing `deepseek_client.chat_json`,
independent of mock mode).

## 7. Evaluation contract

Input: every `Question` in the `QuestionSet` (including hidden
`expected_answer`/`rubric`) + the submitted image(s), sent directly to
DeepSeek's vision-capable model (no local OCR step — see README
"Limitations").

DeepSeek is instructed (see `SYSTEM_PROMPT` in
`backend/app/services/evaluation.py`) to locate each answer in the image(s)
by content (not by position), grade it against the rubric with partial
credit where reasonable, and return:

```jsonc
{
  "overall_feedback": "...",
  "items": [
    {
      "question_order_index": 0,   // matches Question.order_index, not DB id
      "extracted_answer": "...", "marks_awarded": 1, "marks_possible": 1,
      "is_correct": true, "feedback": "..."
    }
  ]
}
```

Items are matched back to `Question` rows by `order_index` (their position
in the set), since the model only sees the paper content, not database IDs.

## 8. Mock mode

Controlled centrally in `config.py` (`effective_mock_mode`): true whenever
`DEEPSEEK_API_KEY` is empty, or `MOCK_MODE=true` is set explicitly. Both
`chat_json` and `vision_json` in `deepseek_client.py` short-circuit to
deterministic placeholder data in this case — same shape a real response
would have, clearly labelled `[MOCK]`. This means:

- The entire UI is click-through-able with zero configuration.
- Automated tests (`backend/tests/`) run without hitting the network.
- Turning on real generation/grading is a one-line `.env` change, not a
  code change.

## 10. Non-goals (by design, for this local/single-family use case)

- No user accounts, login, or multi-tenant isolation.
- No cloud deployment, background job queue, or webhook infrastructure —
  generation and evaluation run synchronously within the HTTP request.
- No payment/quota tracking for DeepSeek usage — that's on DeepSeek's
  dashboard, not this app.

## 11. Natural next steps (not built, but the code is shaped to allow them)

- A local-OCR fallback (Tesseract) ahead of grading, if DeepSeek vision
  accuracy on real handwriting turns out to need it — isolated to
  `evaluation.py`/`deepseek_client.py`. Deliberately not built yet: the
  chosen architecture sends photos straight to DeepSeek's vision model
  (see §7), and this would only be worth adding if that proves unreliable
  in practice.
- Multiple children/profiles if this ever needs to serve more than one kid
  from the same install.
- `GET /api/patterns/schema` already exists (served for tooling/API
  consumers) but the Admin form (§5) doesn't derive itself from it — the
  form's fields were hand-built to match the schema. If the schema changes
  meaningfully, both need updating together today.

## 12. The past-paper bank

### Extraction (`services/paper_extraction.py`), with no OCR and no AI

Cambridge papers are born-digital: real text plus vector diagrams. So
question boundaries come straight from the PDF's coordinates.

- **Finding questions:**
  - Every line that starts with a bold 1–2 digit number in the left
    quarter of the page is a candidate.
  - Candidates are grouped by x position. The group whose numbers run
    1, 2, 3… the longest wins.
  - This discards cover-page barcode digits, graph axis labels, table
    cells and the like.
- **Cropping:**
  - A question spans from its number down to the next question's number.
  - Its crop is the union of the real content in that range: text lines
    and drawing paths. Blank answer/working space after the last line is
    therefore left out automatically.
  - Content ending within 12pt above a question number belongs to that
    question. Tall maths such as fractions and column vectors pokes above
    its number's line, while the previous question always ends about 24pt
    clear.
- **Ignored content:**
  - The page-number header and the footer: syllabus code, © UCLES and
    "Turn over".
  - Notes like "Questions 21 and 22 are printed on the next page",
    "BLANK PAGE" pages, and the copyright paragraph on the last page.
  - Optional "Additional page" lined pages at the end.
- **Multi-page questions:** a question that continues onto later pages
  gets one segment per page. The segments are stitched into one PNG at
  180 dpi, kept as vectors until the final render.
- **Consistent output:**
  - Every crop of a paper spans the same x range, so printed questions
    share one scale.
  - The original question number is whited out so the new paper can
    renumber questions.
- **Marks and sub-parts:** marks are the sum of the `[n]` brackets in the
  question's text, and sub-parts are its `(a)`, `(b)`… lines.

### Mark scheme (`services/mark_scheme.py`)

- **Table layout:**
  - The answer table (Question | Answer | Marks | Partial Marks) is ruled.
  - Columns come from its vertical rules.
  - Each row starts at a label in the Question column (`4`, `8(a)`,
    `11(a)(i)`) and runs to the next label.
  - Overflow at the top of the next page is carried into the previous row.
- **Text:** cell text is assigned word by word, because one PDF line often
  crosses the Marks/Partial Marks boundary. Symbol-font glyphs are mapped
  to Unicode (`×`, `−`, `π`, …).
- **Images:**
  - Stacked maths still comes out scrambled as text, so each question's
    rows are also rendered as an image (the table header followed by its
    rows).
  - That image is what the answer key shows and what the grader is told
    to trust.

### Automatic checks (`services/past_paper_import.py`)

There is no human review step. The checks only attach warnings; nothing is
blocked except failed extraction and duplicates.

| Level | Check |
|---|---|
| Paper | Question numbering stops early while higher numbers still appear |
| Paper | Question marks don't add up to the mark scheme's "Maximum Mark" |
| Paper | The mark scheme has answers for questions that weren't found |
| Paper | The mark scheme's code/session doesn't match the question paper's |
| Paper | No mark scheme uploaded (informational) |
| Paper | Topic tagging failed (informational) |
| Question | No `[n]` mark allocation found |
| Question | No mark-scheme entry |
| Question | Marks differ from the mark scheme's Marks column (`2`, `2 2`, `M1 A1`, `2 B1`, `1FT`; skipped when a cell holds anything else) |
| Question | Crop spans 3+ pages |

Failures and duplicates are handled as follows:

- A paper with no text layer (a scan) or no detectable question numbers
  is marked `failed` with the reason.
- Re-uploading a paper that's already in the bank (same code and session)
  is refused as `failed`, so its questions can't appear twice.

### Topics (`services/topic_tagging.py`)

One DeepSeek call per paper gives each question 1–3 topics, preferring a
fixed suggested vocabulary so names stay consistent across papers. This is
best-effort: in mock mode, or on any error, questions stay untagged.

### Building sets (`services/bank_sets.py`, `POST /question-sets/from-bank`)

- **Request fields:**
  - `target_marks`
  - `num_sets` (1–10)
  - optional `past_paper_ids` and `topics` (either empty = all)
  - `avoid_used` (default true): skip questions already used in any
    earlier set
  - `include_flagged` (default false)
- **Selection:**
  - Questions are drawn at random until the target is reached.
  - Up to 60 random orderings are tried, and the closest total that
    doesn't exceed the target wins.
  - Sets built in one request never share a question.
  - Picked questions print in original question-number order, which on
    Cambridge papers runs roughly easy to hard.
- **Shortfall:** a set that falls short of the target is still created,
  with a note in `error_message`. If nothing matches at all, the request
  returns a 400 error.
- **Answer key:** each question's `expected_answer`/`rubric` are filled
  from its mark-scheme rows.

### Printing and grading

- **Printable set:** shows each question image, renumbered, followed by
  working space of about 1.5cm per mark (2–10cm), because the crop leaves
  out the paper's original blank space.
- **Answer key:** adds the source (e.g. `0444/21 May/June 2023 Q9`) and
  the mark-scheme image.
- **Grading:**
  - The mark-scheme images for bank questions are sent to the vision model
    ahead of the student's photos, and the prompt says which image is which.
  - The prompt also explains the M/A/B/FT mark codes.
